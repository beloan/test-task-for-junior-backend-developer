# Task Service

Сервис для управления задачами с HTTP API на Go.

## Новая функциональность: Периодические задачи

Реализована поддержка периодических (повторяющихся) задач. Врачи теперь могут настраивать периодичность выполнения задач (ежедневно, еженедельно, ежемесячно и т.д.) и получать расписание предстоящих выполнений.

### Типы периодичности

1. **none** - задача не периодическая (по умолчанию)
2. **daily** - ежедневно каждый N-й день
3. **monthly** - ежемесячно на определено число (1-30)
4. **weekly** - еженедельно на конкретные дни (0=Пн, 1=Вт, ..., 6=Вс)
5. **odd_even** - только четные или только нечетные дни месяца
6. **specific** - на конкретные даты

### Структура RecurrenceConfig

```json
{
  "recurrence_type": "daily|monthly|weekly|odd_even|specific|none",
  "interval_days": 1,                          // для daily - каждый N-й день
  "monthly_day_of_month": 15,                  // для monthly - число месяца (1-30)
  "weekly_days": [0, 2, 4],                   // для weekly - дни недели
  "odd_even_type": "odd|even",                // для odd_even
  "specific_dates": ["2024-04-10", "2024-12-25"],  // для specific
  "end_date": "2024-12-31T23:59:59Z",         // конец периодичности (опционально)
  "max_occurrences": 100                      // максимум выполнений (опционально)
}
```

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## API

Базовый префикс API:

```text
/api/v1
```

### Основные маршруты

#### Создание задачи
- `POST /api/v1/tasks`

**Пример запроса:**
```json
{
  "title": "Ежедневный обзвон пациентов",
  "description": "Обзвон всех активных пациентов",
  "status": "new",
  "recurrence": {
    "recurrence_type": "daily",
    "interval_days": 1
  }
}
```

#### Получение всех задач
- `GET /api/v1/tasks`

#### Получение задачи по ID
- `GET /api/v1/tasks/{id}`

#### Получение расписания (следующих дат выполнения) для периодической задачи
- `GET /api/v1/tasks/{id}/schedule?limit=10`

**Параметры:**
- `limit` (опционально) - количество следующих дат для показа (по умолчанию 10, максимум ограничен конфигурацией периодичности)

**Пример ответа:**
```json
{
  "task_id": 1,
  "recurrence_type": "daily",
  "schedule": [
    "2024-04-07T10:00:00Z",
    "2024-04-08T10:00:00Z",
    "2024-04-09T10:00:00Z"
  ]
}
```

#### Обновление задачи
- `PUT /api/v1/tasks/{id}`

#### Удаление задачи
- `DELETE /api/v1/tasks/{id}`

## Архитектурные решения

### 1. Хранение конфигурации в JSONB

**Выбор:** Конфигурация периодичности хранится в `JSONB` поле в PostgreSQL вместо отдельных полей для каждого типа.

**Обоснование:**
- Гибкость: разные типы периодичности требуют разные параметры
- Расширяемость: легко добавить новые типы периодичности
- Производительность: индексирование JSONB быстро
- Простота: одно поле вместо множества NULL-полей

### 2. Паттерн Strategy для генерирования расписания

**Выбор:** Каждый тип периодичности имеет отдельный метод генерирования в `RecurrenceGenerator`.

**Обоснование:**
- Чистота кода: каждый метод отвечает за один тип
- Тестируемость: легко писать юнит-тесты для каждого типа
- Расширяемость: новые типы добавляются без изменения существующей логики

### 3. Расписание генерируется на-лету

**Выбор:** Даты выполнения не сохраняются в БД, а генерируются динамически при запросе.

**Обоснование:**
- Экономия памяти: нет множества строк в БД
- Гибкость: легко изменить конфигурацию
- Масштабируемость: нет проблем с росту количества записей

### 4. Валидация на уровне usecase

**Выбор:** Конфигурация периодичности валидируется в сервисе перед сохранением.

**Обоснование:**
- Консистентность: недопустимые конфигурации не попадают в БД
- Четкие ошибки: пользователь видит точную причину ошибки
- Бизнес-логика: usecase отвечает за правила приложения

## Граничные случаи

### 1. Месячные задачи в февралю

Если задача на 30-е число и наступает февраль, она автоматически ставится на последний день месяца (28 или 29).

### 2. Задачи без периодичности

Если `recurrence_type = "none"` (по умолчанию), новый эндпоинт `/schedule` вернет пустой массив.

### 3. Конец периодичности (endDate)

Если указана `end_date`, задачи не генерируются после этой даты.

### 4. Максимум выполнений (maxOccurrences)

Если задана `max_occurrences`, будет сгенерировано максимум указанное количество дат.

### 5. Валидация дат в specific

При указании конкретных дат проверяется формат (YYYY-MM-DD) и валидность даты.

## Примечания

1. **Часовой пояс**: Даты в расписании возвращаются в UTC (ISO 8601 формат)
2. **Timezone handling**: Хранение времени в БД в UTC, преобразование на клиенте
3. **Производительность**: RecurrenceGenerator кешируется в памяти для одной задачи, может быть улучшено с Redis если потребуется
4. **Ограничения**: Максимум 365 сгенерированных дат в одном запросе
