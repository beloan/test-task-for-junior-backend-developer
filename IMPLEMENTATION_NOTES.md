# Реализация функции периодических задач

## Обзор реализации

Добавлена полная поддержка периодических (повторяющихся) задач в трекер задач. Система позволяет врачам и персоналу настраивать различные типы периодичности для своих задач.

## Компоненты реализации

### 1. Модели и типы (domain/task)

#### `recurrence.go`
- Определяет типы периодичности (RecurrenceType)
- Структура конфигурации (RecurrenceConfig) с параметрами
- Валидация конфигурации

**Типы периодичности:**
- `none` - без периодичности (по умолчанию)
- `daily` - каждый N-й день
- `monthly` - в определенное число месяца
- `weekly` - в определенные дни недели
- `odd_even` - четные или нечетные дни
- `specific` - конкретные даты

#### `recurrence_generator.go`
- Класс RecurrenceGenerator для генерирования расписаний
- Методы для каждого типа периодичности
- Поддержка ограничений (endDate, maxOccurrences)

### 2. Слой данных

#### `migrations/0002_add_recurrence.{up,down}.sql`
- Добавляет 3 новых колонки к таблице tasks:
  - `recurrence_type` - тип периодичности
  - `recurrence_config` - JSONB конфигурация
  - `recurrence_end_date` - дата окончания
- Триггер для валидации типа периодичности на уровне БД

#### `repository/postgres/task_repository.go`
- Обновлены все методы для работы с полями периодичности
- Сериализация/десериализация конфигурации в JSON
- Правильная обработка NULL значений

### 3. Бизнес-логика (usecase/task)

#### `service.go`
- Добавлена валидация конфигурации периодичности
- Новый метод `GetSchedule()` для получения расписания
- Проверка правильности входных данных

#### `ports.go`
- Обновлены структуры CreateInput и UpdateInput
- Новый интерфейс метода GetSchedule

### 4. HTTP слой

#### `handlers/task_handler.go`
- Обновлены handlers для Create и Update
- Новый handler GetSchedule с поддержкой параметра limit
- Корректная обработка ошибок

#### `handlers/dto.go`
- Добавлено поле Recurrence к taskMutationDTO и taskDTO
- Поддержка сериализации/десериализации

#### `router.go`
- Новый маршрут: `GET /api/v1/tasks/{id}/schedule`

## Примеры использования

### Создание периодической задачи
```bash
curl -X POST http://localhost:8080/api/v1/tasks \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Ежедневный обзвон",
    "description": "Обзвон активных пациентов",
    "status": "new",
    "recurrence": {
      "recurrence_type": "daily",
      "interval_days": 1
    }
  }'
```

### Получение расписания
```bash
curl "http://localhost:8080/api/v1/tasks/1/schedule?limit=5"
```

Ответ:
```json
{
  "task_id": 1,
  "recurrence_type": "daily",
  "schedule": [
    "2024-04-07T10:23:45Z",
    "2024-04-08T10:23:45Z",
    "2024-04-09T10:23:45Z",
    "2024-04-10T10:23:45Z",
    "2024-04-11T10:23:45Z"
  ]
}
```

## Граничные случаи и обработка

### 1. Месячные задачи
- Если число > дней в месяце (например 31 в феврале), использует последний день
- Пример: 30-е число будет переведено на 28-29 февраля

### 2. Еженедельные задачи
- Дни недели: 0=Пн, 1=Вт, ... 6=Вс
- Проверка диапазона [0-6]

### 3. Конкретные даты
- Формат: YYYY-MM-DD
- Циклическое повторение с переходом на следующие годы

### 4. Nonceilin завернутые на 10 лет
- Диапазон генерирования: текущий год + 10 лет
- Ограничение памяти для больших limit значений

### 5. EndDate и MaxOccurrences
- Если оба указаны, действует первое достигнутое ограничение
- Валидируется при создании/обновлении

## Архитектурные решения

### Почему JSONB для хранения конфигурации?

1. **Гибкость** - разные типы требуют разные параметры
2. **Масштабируемость** - новые типы без миграций БД
3. **Нормализация** - недостаточно отдельных полей для всех вариантов
4. **Производительность** - индексирование JSONB эффективно

### Почему генерировать даты на-лету?

1. **Экономия памяти** - не сохраняем X дат в БД
2. **Гибкость** - изменение конфигурации автоматически обновляет расписание
3. **Производительность** - быстрое создание/обновление задач
4. **Простота** - нет синхронизации между таблицами

### Валидация на уровне usecase

Конфигурация валидируется перед сохранением для:
- Обеспечения консистентности БД
- Предоставления четких ошибок пользователю
- Разделения ответственности (бизнес-логика в usecase)

### Примеры unit-тестов для RecurrenceGenerator

```go
func TestDailyRecurrence(t *testing.T) {
    config := RecurrenceConfig{RecurrenceType: "daily", IntervalDays: &2}
    gen, _ := NewRecurrenceGenerator(config)
    dates := gen.GenerateNextOccurrences(time.Now(), 3)
    // проверяем что даты через 2 дня
}

func TestMonthlyRecurrence(t *testing.T) {
    config := RecurrenceConfig{RecurrenceType: "monthly", MonthlyDayOfMonth: &30}
    gen, _ := NewRecurrenceGenerator(config)
    dates := gen.GenerateNextOccurrences(time.Now(), 3)
    // проверяем 30 число каждого месяца
}
```

## Возможные улучшения

1. **Кеширование расписаний** - Redis для часто запрашиваемых задач
2. **Фоновая работа** - автоматическое создание экземпляров для выполнения
3. **Уведомления** - reminders за N часов до выполнения
4. **История выполнения** - отслеживание когда была выполнена задача
5. **Более сложные правила** - рекуррентность по типу "второе вторник месяца"
6. **Интеграция с календарем** - синхронизация с Google Calendar, Outlook

## Замечания по развертыванию

1. Новая миграция БД применяется автоматически при запуске Docker Compose
2. Если используется существующий volume, нужно удалить и пересоздать: `docker compose down -v`
3. Swagger UI будет обновлен автоматически (если используется)
4. Backward compatible - старые задачи продолжат работать с `recurrence_type = "none"`

## Дополнительно

- Все даты хранятся и возвращаются в UTC (ISO 8601)
- Клиент должен преобразовать UTC в локальный timezone
- Конфигурация периодичности валидируется и на сервере, и на клиенте (если используется)
